# HTTP authorization inventory

This inventory is the review checklist for every registered core and plugin HTTP
operation. A route is either **public** or **protected**; there is no implicit
classification. Paths ending in `/{id}` include every listed method. The
authorization tests must state expected status codes directly rather than derive
them from application guards.

The exact, machine-enforced operation lists are
[`authorization_routes.tsv`](authorization_routes.tsv) for the fully composed
backend and
[`frontend_authorization_routes.tsv`](frontend_authorization_routes.tsv) for
core and shipped-plugin frontend routes. The tables below remain the human policy
description. Structural tests compare the manifests with the registered FastAPI
application, the React Router configuration, and every shipped plugin route
contribution, so adding a route requires an explicit `public` or `protected`
classification.

The structural gates and behavioral authorization suites remain independently
runnable:

```sh
uv run --package sta-integration-tests --directory tests/backend pytest test_authorization_inventory.py
uv run --package sta --directory core/backend pytest test/api/test_authorization_matrix.py
uv run --package sta-integration-tests --directory tests/backend pytest test_plugin_authorization_conformance.py
npm run test:unit --workspace=sta -- --run test/app/AuthorizationRouteInventory.test.ts
npm run test:unit --workspace=sta -- --run test/app/routes/AuthorizationMatrix.test.tsx test/app/routes/GuardedMutationRoutes.test.ts
```

The ordinary `bash scripts/test.sh backend` and `bash scripts/test.sh frontend`
paths discover these tests, so the same structural checks run in continuous
integration without a root npm alias.

Profiles used below are `anonymous`, `no-roles`, `annotator`, `supervisor`,
`project-manager`, `data-manager`, `admin`, and the
`project-manager` + `data-manager` dual-role profile. A protected operation
returns `401` without a valid access token. Resource filtering and deliberately
concealed resources can produce `404` even where a role is otherwise sufficient.

## Plugin operations

Reads use the same data-reader and resource-visibility policy as their core group;
writes require `data-manager`. Editor plugin routes additionally require a valid
signed-in editor principal and the source/frame constraints noted below.

## Known policy questions

No uncertain policy is encoded as an allow expectation here. The exact `403`
versus concealed `404` result for scoped source/label collection and item reads,
and whether segmentation assistant proxy endpoints must independently validate
the supplied PCD identifier, must be pinned from existing product rules before
Phase 2 adds behavioral cases for those edges.

Phase 2 also found two conflicts between this intended inventory and the current
HTTP behavior. A signed-in user with no application roles currently receives a
filtered `200` from both `GET /source/groups` and `GET /label/groups`, rather
than the inventory's role-level `403`. A project manager currently receives
`200` from `DELETE /projects/{id}` and the project is deleted, although the
inventory and frontend rule reserve project deletion for administrators. These
behaviors remain excluded from allow-contract tests until the product policy is
confirmed; no implementation change follows from this inventory alone.

Phase 4 therefore covers project-manager project, task, and frame management
through the existing browser workflow but does not encode project deletion as
either allowed or refused. The current backend allows it while the documented
policy reserves it for administrators; a browser assertion is blocked until
that product-policy conflict is resolved.

The checkpoint endpoint currently accepts a branch `WRITE` grant, while the
initial inventory classified checkpoint/history changes as `WRITE_ELEVATED`.
Phase 2 does not assert either policy until that distinction is confirmed.
